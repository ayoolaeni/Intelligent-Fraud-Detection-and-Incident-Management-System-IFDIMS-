## 1. System overview

IFDIMS receives banking transactions in near real time, scores each one with a trained machine learning model, explains the score with SHAP, places it in a risk band, raises alerts, automatically opens incident cases for high-risk transactions, and lets fraud analysts and supervisors manage each case through a defined workflow on a web dashboard. Every action is written to an audit log.

### 1.1 Actors and roles

| Actor | How they access the system | Main tasks |
|---|---|---|
| **Fraud Analyst** (`analyst`) | Web dashboard (login) | View alerts and SHAP explanations; investigate assigned cases; add notes and attachments; update case status; escalate cases |
| **Supervisor** (`supervisor`) | Web dashboard (login) | Everything an analyst can do, plus assign/reassign cases, handle escalations, approve case closure, reopen cases, view reports |
| **Administrator** (`admin`) | Web dashboard (login) | Manage users and roles; configure risk thresholds and SLA times; manage and activate model versions; view audit logs; export labels |
| **Transaction System** (service) | REST API with an API key | Submit transactions for scoring (represents the bank's channels; simulated in this project) |

### 1.2 End-to-end flow

1. The Transaction System calls `POST /api/v1/transactions/score` with a transaction.
2. The back end validates it, stores it, and computes behavioural features from the account's history (Section 5).
3. The active model predicts a fraud probability (`fraud_score`, 0 to 1) and SHAP computes the top contributing features.
4. The score is mapped to a risk band using the configurable thresholds (default: low < 0.40 ≤ medium ≤ 0.70 < high).
5. Actions by band:
   - **Low:** approve, store prediction, write audit log.
   - **Medium:** approve, store prediction, create an **alert** for review.
   - **High:** **hold** the transaction, store prediction, create an alert, **automatically open a case**, and notify analysts.
6. Analysts and supervisors work the alert/case on the dashboard until it is closed. Resolved outcomes (confirmed fraud / false positive) become labels for retraining.

### 1.3 Scope boundaries (from Chapter One)

- Channels: NIP interbank transfer, mobile app, USSD, internet banking, POS, ATM.
- No integration with a real core banking system, card switch or NIBSS. A **simulator** plays the role of the bank's channels.
- No biometric/liveness verification. No cheque, loan or financial-statement fraud.
- Models are trained on public benchmark datasets and a synthetic Nigerian dataset generated by this project.

### 4.3 Synthetic data generator (`ml/generator/generate_synthetic.py`)

Command line:

```
python -m generator.generate_synthetic --out data/synthetic/train --customers 5000 --days 90 --seed 42 --fraud-rate 0.005
python -m generator.generate_synthetic --out data/synthetic/demo  --customers 1000 --days 60 --seed 7  --fraud-rate 0.02
```

Outputs (CSV): `customers.csv`, `accounts.csv`, `transactions.csv`, `security_events.csv`, `summary.json` (row counts, fraud share by scenario and channel).

The target for the training world is about 500,000 transactions with a fraud share under 1%. Use NumPy's `default_rng(seed)` everywhere so runs are reproducible.

**Customers and accounts**

- Each customer: `customer_id`, `full_name` (random Nigerian first/last names from a built-in list of at least 100 each), `bvn` (11 random digits, hashed on load), `phone` (`080/081/070/090/091` + 8 digits, hashed on load), `date_joined` (between 5 years and 7 days before the start date), `segment`.
- Segments and parameters:

| Segment | Share | Daily txn rate (Poisson λ) | Amount (lognormal, NGN) median | Preferred channels (weights) |
|---|---|---|---|---|
| student | 20% | 1.0 | 3,000 | MOBILE .4, USSD .3, POS .2, ATM .1 |
| salaried | 40% | 1.8 | 15,000 | MOBILE .35, NIP .25, POS .2, INTERNET .1, ATM .1 |
| trader | 25% | 3.0 | 40,000 | NIP .35, MOBILE .3, USSD .15, POS .1, ATM .1 |
| business | 15% | 4.0 | 150,000 | NIP .45, INTERNET .35, MOBILE .2 |

- Lognormal sigma = 1.0 for all segments; cap single legitimate amounts at 20,000,000.
- Each customer has 1 account (80%) or 2 accounts (20%). `account_type` is `SAVINGS` or `CURRENT` (business → CURRENT). 5% of accounts are opened in the last 30 days (new accounts).
- Each account has 1–2 known devices, a home location (Lagos 45%, Abuja 12%, Rivers 8%, Kano 7%, Oyo 7%, others spread across the remaining states), and 5–30 known beneficiaries.
- Starting balance: 5–60 × the segment median amount. Update the balance after each transaction; add salary/credit inflows (not scored) so balances do not go to zero: on the 25th of each month for `salaried`, and randomly for others.

**Legitimate transactions**

- Hour of day: sample from a daytime-heavy distribution (peak 09:00–20:00; 3% between 00:00 and 05:00).
- 90% from a known device, 95% at home location, 85% to a known beneficiary (for transfers).
- "Hard negatives" (to stop the model learning trivial rules): 1% of legitimate transfers go to a new beneficiary with an amount 3–10× the account's average (e.g. rent, school fees); 2% of legitimate transactions happen while travelling (different location, known device).
- Legitimate security events: about 1 PIN/password reset per account per year, and SIM swaps at 0.5% of accounts over the period, followed by normal behaviour.

**Fraud scenarios** (inject until the target fraud rate is reached; weights in brackets). Set `is_fraud = 1` and `fraud_type` on each fraudulent transaction.

1. **SOCIAL_ENGINEERING** (35%): victim's own known device and location; one or two `NIP`/`MOBILE` transfers to a **new beneficiary**; amount 40–95% of balance; often outside usual hours (40% chance between 19:00 and 23:59).
2. **ACCOUNT_TAKEOVER** (25%): a `PASSWORD_RESET` or `NEW_DEVICE_ENROLLED` event 10 minutes to 24 hours earlier; **new device**, **different location**; 2–6 transfers to new beneficiaries within 60 minutes that together drain 60–100% of the balance.
3. **SIM_SWAP** (20%): a `SIM_SWAP` event 30 minutes to 48 hours earlier; new device; `USSD` or `MOBILE` transfers; 2–5 transfers within 2 hours; new beneficiaries.
4. **CARD_FRAUD** (20%): `POS`, `ATM` or `INTERNET` `CARD_PAYMENT`/`WITHDRAWAL`; different location; new terminal/device IDs; 3–8 transactions within 3 hours; amounts 5,000–200,000 each.

About 20% of fraud should target new accounts (account age < 30 days) or go to beneficiaries that are themselves new accounts (mule accounts).

Also add **2% label noise** in the training world only (flip a small, random share of fraud labels to 0 to reflect unreported fraud), and record it in `summary.json`.

## 5. Feature definitions (single source of truth: `ml/fraud_core/features.py`)

These features implement Chapter Three, Table 3.2. For a transaction `t` of account `a` at time `T`, "history" means **only** that account's transactions with `txn_time < T` (never the current or future ones) and security events with `event_time <= T`.

| # | Feature name (column) | Definition |
|---|---|---|
| 1 | `log_amount` | `ln(1 + amount)` |
| 2 | `amount_to_avg_30d` | `amount / mean(amount of history in (T − 30 days, T))`. If no history in that window: `amount / GLOBAL_MEDIAN_AMOUNT` (constant saved with the model). Cap at 100. |
| 3 | `hour_sin`, `hour_cos` | `sin(2π·h/24)`, `cos(2π·h/24)` where `h` = hour of `T` in Africa/Lagos time |
| 4 | `is_night` | 1 if hour is 00:00–04:59, else 0 |
| 5 | `day_of_week` | 0 = Monday … 6 = Sunday |
| 6 | `channel_NIP`, `channel_MOBILE`, `channel_USSD`, `channel_INTERNET`, `channel_POS`, `channel_ATM` | One-hot channel |
| 7 | `txn_count_1h`, `txn_count_24h` | Number of history transactions in the last 1 hour / 24 hours |
| 8 | `txn_sum_1h`, `txn_sum_24h` | Log of (1 + total amount) of history transactions in the last 1 hour / 24 hours |
| 9 | `mins_since_last_txn` | Minutes since the most recent history transaction; if none, 43,200 (30 days). Cap at 43,200. |
| 10 | `is_new_device` | 1 if `device_id` is not null and has not appeared in any history transaction of the account, else 0 |
| 11 | `is_new_beneficiary` | For `TRANSFER`: 1 if `beneficiary_account` never appears in the account's history; else 0. For other types: 0. |
| 12 | `is_location_change` | 1 if `location` differs from the most frequent location in the last 30 days of history; 0 if equal or no history |
| 13 | `recent_security_event_48h` | 1 if any `SIM_SWAP`, `PIN_RESET`, `PASSWORD_RESET` or `NEW_DEVICE_ENROLLED` event exists in `[T − 48h, T]`, else 0 |
| 14 | `account_age_days` | Days between account `opened_on` and `T` (float), minimum 0 |
| 15 | `balance_ratio` | `amount / balance_before`; if `balance_before <= 0` then 1.0; cap at 1.0 |

The ordered list of feature column names lives in `fraud_core/constants.py` as `FEATURE_NAMES` (23 columns, in the order of the table above). The model stores this list and scoring must refuse to run if the model's list differs.

### 5.1 Two implementations, one definition

- `compute_features_online(txn, history_txns, security_events, account, global_median) -> dict` — used by the back end for one transaction. `history_txns` is the list of the account's prior transactions from the last 30 days (plus the set of all prior devices and beneficiaries, see 7.4 for fast queries).
- `compute_features_batch(transactions_df, security_events_df, accounts_df, global_median) -> DataFrame` — used by the training pipeline. Sort by `account_number, txn_time`; for each account iterate in time order, maintaining rolling windows (deque), seen-device and seen-beneficiary sets and a location counter. Vectorise where possible, but correctness comes first.
- Both must produce identical values (parity test, Section 15.2).

## 6. Machine learning pipeline (`ml/pipeline/`)

Implements Chapter Three, Sections 3.2.5–3.2.7 and Figure 3.1.

### 6.1 Steps

1. **Build features:** `python -m pipeline.build_features --in data/synthetic/train --out data/processed/train_features.parquet`. Compute `GLOBAL_MEDIAN_AMOUNT` from the training transactions and save it to `data/processed/feature_meta.json`.
2. **Split:** stratified random split on `is_fraud`: 70% train, 15% validation, 15% test (`random_state=42`). Save the split indices.
3. **Balance the training set only:**
   - Logistic Regression, Random Forest: two variants each — (a) SMOTE (`imblearn.over_sampling.SMOTE`, `sampling_strategy=0.1`, `k_neighbors=5`) and (b) class weights (`class_weight="balanced"`). Keep the better variant on validation PR-AUC.
   - XGBoost: two variants — (a) SMOTE as above, (b) `scale_pos_weight = n_negative / n_positive`.
   - Never apply SMOTE to validation or test data.
   - Use an `imblearn.pipeline.Pipeline` so SMOTE only runs inside training folds during cross-validation.
4. **Scale:** `StandardScaler` for Logistic Regression only (inside the pipeline). Tree models use raw features.
5. **Train and tune** with `StratifiedKFold(n_splits=5, shuffle=True, random_state=42)` and `RandomizedSearchCV` (`n_iter=20`, scoring = `average_precision`):

| Model | Search space |
|---|---|
| LogisticRegression (`max_iter=2000`, `solver="liblinear"`) | `C` ∈ {0.01, 0.1, 1, 10}, `penalty` ∈ {l1, l2} |
| RandomForestClassifier (`n_jobs=-1`) | `n_estimators` ∈ {100, 200, 400}, `max_depth` ∈ {8, 12, 16, None}, `min_samples_leaf` ∈ {1, 2, 5} |
| XGBClassifier (`tree_method="hist"`, `eval_metric="aucpr"`) | `n_estimators` ∈ {200, 400, 600}, `max_depth` ∈ {3, 5, 7}, `learning_rate` ∈ {0.03, 0.1, 0.2}, `subsample` ∈ {0.7, 0.9, 1.0}, `colsample_bytree` ∈ {0.7, 0.9, 1.0} |
| IsolationForest (unsupervised, trained on training data without labels) | `n_estimators` ∈ {100, 300}, `contamination` ∈ {"auto", 0.005, 0.01} — score = min-max normalised negative `score_samples` so that higher = more anomalous |

6. **Evaluate** every model on the **validation** set (for selection) and on the **test** set (for reporting), with:
   - Precision, Recall, F1 (at the chosen threshold), False Positive Rate — Equations 3.1–3.4 in Chapter Three.
   - ROC-AUC and PR-AUC (`average_precision_score`).
   - Confusion matrix.
   - Average scoring time per transaction (ms), measured on 1,000 single-row predictions including SHAP.
7. **Select the model:** among the supervised models, pick the highest validation PR-AUC. If two are within 0.005, prefer the one with lower latency. Isolation Forest is reported for comparison but is not eligible for deployment.
8. **Set thresholds** on the validation set:
   - Report the precision/recall at the default thresholds 0.40 and 0.70.
   - Also compute a suggested `high` threshold that gives precision ≥ 0.80 with the highest recall, and a suggested `medium` threshold that gives recall ≥ 0.95. Save both as `suggested_thresholds` in the model metadata. The live thresholds stay at the defaults until an admin changes them in Settings.
9. **Build the SHAP explainer:** `shap.TreeExplainer` for Random Forest/XGBoost (use the probability output for the positive class); `shap.LinearExplainer` for Logistic Regression (explain the scaled features; map back to original names). Save the explainer's background/expected value with the model.
10. **Save the model bundle** to `models/<version>/`:
    - `model.joblib` — dict: `{"estimator", "feature_names", "global_median_amount", "algorithm", "version", "trained_at", "suggested_thresholds", "shap_expected_value"}`
    - `metadata.json` — metrics (validation and test), best hyperparameters, dataset summary, training time.
    - `version` format: `YYYYMMDD-HHMM-<algorithm>` (e.g. `20261015-1430-xgboost`).
11. **Register:** `python -m pipeline.register_model --path models/<version>` inserts a `model_version` row (Section 7), with `is_active=false`. `--activate` also makes it active.

### 6.3 Public benchmark comparison (`ml/pipeline/benchmark_public.py`)

### 7.4 Fast history queries for online features

1. Transactions of the account with `txn_time` in `[T − 30 days, T)` (amount, time, location, device, beneficiary).
2. `EXISTS` query: has `device_id` been used before `T` by this account?

4. Security events of the account in `[T − 48 h, T]`.

### 8.2 Transaction scoring (FR1–FR7)

**`POST /transactions/score`** (API key)

Request:
```json
{
  "txn_ref": "NIP-20261015-000123",
  "account_number": "0123456789",
  "amount": "250000.00",
  "channel": "NIP",
  "txn_type": "TRANSFER",
  "txn_time": "2026-10-15T21:42:10+01:00",
  "beneficiary_account": "9876543210",
  "beneficiary_bank": "058",
  "device_id": "dev-7f3a",
  "location": "Lagos",
  "balance_before": "310000.00"
}
```

Processing (in one DB transaction):

1. Validate. Unknown `account_number` → 404. Duplicate `txn_ref` → return the **existing** result with HTTP 200 (idempotent).
2. Insert into `txn` with status `APPROVED` (updated below).
3. Load history (7.4), compute features.
4. Predict `fraud_score` with the active model; compute SHAP; keep the top 5 factors by absolute contribution **that increase** the score first, then the rest.
5. Band: `high` if score > high threshold; `medium` if score ≥ medium threshold; else `low`.
6. Insert `prediction` (with features, SHAP, latency).
7. If medium → insert alert (`severity=medium`, `status=OPEN`).
8. If high → insert alert (`severity=high`); if `hold_high_risk` set `txn.status=HELD`; create a case (Section 10.2) and notify (Section 11).
9. Audit `TXN_SCORED` (actor `api:<name>`).

Response `200`:
```json
{
  "txn_id": "…", "prediction_id": "…",
  "fraud_score": 0.8731, "risk_band": "high",
  "decision": "HOLD",
  "alert_id": "…", "case_id": "…", "case_number": "FC-2026-000123",
  "top_factors": [
    {"feature": "is_new_beneficiary", "label": "New beneficiary", "raw_value": 1, "contribution": 0.412, "description": "Beneficiary has never been paid before"}
  ],
  "model_version": "20261015-1430-xgboost",
  "latency_ms": 38.5
}
```
`decision` is `APPROVE` or `HOLD`. If there is no active model, return `503` with code `NO_ACTIVE_MODEL`.

## 10. Incident case workflow (Chapter Three, Figure 3.7, Table 3.7)

### 10.1 States

`NEW` → `ASSIGNED` → `UNDER_INVESTIGATION` → (`ESCALATED`) → `RESOLVED` → `CLOSED`

### 10.2 Case creation and priority

- From a **high** alert (automatic): priority `critical` if `amount ≥ critical_amount_ngn`, else `high`. Title: `"High-risk <channel> <txn_type> of ₦<amount> on account ****<last4>"`. `amount_at_risk` = transaction amount. If `auto_assign` is true, assign to the active analyst with the fewest open cases (then `ASSIGNED`); otherwise `NEW`.
- From a **medium** alert (analyst/supervisor action): priority `medium` (or `high` if amount ≥ `critical_amount_ngn`).
- **Customer report / manual:** priority given, default `medium`. `low` is used for follow-ups and reviews.
- On creation compute `ack_due_at = opened_at + sla[priority].ack_minutes` and `resolve_due_at = opened_at + sla[priority].resolve_minutes`.
- `case_number` = `FC-<year>-<6-digit sequence>` (PostgreSQL sequence).
- Add a `SYSTEM` note describing why the case was opened (score, band, top 3 factors).

### 10.3 Allowed transitions

| From | To | Who | Required input | Side effects |
|---|---|---|---|---|
| NEW | ASSIGNED | supervisor (via `/assign`), or system (auto-assign) | assignee | notify assignee |
| ASSIGNED | UNDER_INVESTIGATION | assigned analyst or supervisor | — | set `acknowledged_at` |
| UNDER_INVESTIGATION | ESCALATED | assigned analyst or supervisor | note (reason) | notify all supervisors |
| NEW, ASSIGNED, UNDER_INVESTIGATION | ESCALATED | system (SLA job) | — | system note "SLA breached: acknowledge/resolve"; notify supervisors |
| ESCALATED | UNDER_INVESTIGATION | supervisor | note (instructions) | notify assignee |
| UNDER_INVESTIGATION | RESOLVED | assigned analyst or supervisor | note, `outcome`, `fraud_type` (if confirmed), `amount_recovered` (optional) | set `resolved_at`; held txn → `DECLINED` if `confirmed_fraud`, `APPROVED` if `false_positive`; if confirmed, set customer `risk_profile = high` |
| ESCALATED | RESOLVED | supervisor | same as above | same as above |
| RESOLVED | CLOSED | supervisor | note (optional) | set `closed_at`; alert status stays `CASE_OPENED` |
| RESOLVED | UNDER_INVESTIGATION | supervisor (reject resolution) | note | clear `resolved_at`, keep outcome as draft |
| CLOSED | UNDER_INVESTIGATION | supervisor (reopen) | note (reason) | clear `closed_at`/`resolved_at`; new `resolve_due_at` from now; notify assignee |

A case escalated by the SLA job may have no assignee: the supervisor uses `/assign` (the status stays `ESCALATED`) before returning it. `ESCALATED → UNDER_INVESTIGATION` is refused with `409 NO_ASSIGNEE` if nobody is assigned.

Any other transition returns `409` with code `INVALID_TRANSITION`. Implement the table as data (a dict) in `case_service.py` and generate `allowed_transitions` for the UI from the same data. Every transition writes a `STATUS_CHANGE` note and an audit entry with before/after status.

### 10.4 SLA job (`sla_service.py`)

Runs every 60 seconds (APScheduler, started on app startup; guarded so only one instance runs — use a PostgreSQL advisory lock):

- Cases in `NEW`/`ASSIGNED` with `now > ack_due_at` → escalate (system).
- Cases not in `RESOLVED`/`CLOSED`/`ESCALATED` with `now > resolve_due_at` → escalate (system).
- Do not escalate the same case twice for the same breach (store the breach type in the note/audit and check it).

## 13. Security requirements (Chapter Three, Section 3.6.2)

- Passwords: bcrypt (cost 12). Never log passwords or tokens.
- JWT secret from environment (`JWT_SECRET`, at least 32 random characters); the app refuses to start with the example value when `APP_ENV=production`.
- HTTPS: provided by the reverse proxy in deployment; document it. In local Docker, HTTP is acceptable.
- CORS: only the front-end origin.
- Input validation with Pydantic; SQLAlchemy only (no raw string-built SQL).
- BVN and phone numbers stored as salted SHA-256 hashes (`BVN_SALT`, `PHONE_SALT` in environment).
- Rate limit `/auth/login` (5 per minute per IP) and `/transactions/score` (configurable, default 200 per second per key) — a simple in-memory limiter is acceptable, noted in `DECISIONS.md`.
- File uploads: type and size checks; random stored file names; served only to authorised users.
- Security headers in Nginx (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, a basic `Content-Security-Policy`).
- Audit log for all logins and all changes.

## 15. Testing (Chapter Three, Section 3.9)

Target ≥ 80% line coverage for `backend/app` and `ml/fraud_core`. `make test` runs everything.

### 15.1 Unit tests

- `fraud_core.features`: each feature on hand-made examples, including edge cases (no history, zero balance, non-transfer beneficiary, midnight, caps).
- Risk band mapping at the exact boundaries (0.3999, 0.40, 0.70, 0.7001).
- Case state machine: every allowed transition succeeds; every disallowed one raises; role checks.
- Priority and SLA due-date calculation.
- SLA job: breaches escalate once; non-breaches untouched.
- Settings validation.
- Password hashing, JWT creation/expiry, API key check.
- Report CSV columns.

### 15.2 Feature parity test (mandatory)

Generate a small synthetic world (200 customers, 14 days), load it into a test database, then for 300 randomly chosen transactions compare `compute_features_batch` output with the online path (`feature_service` reading from the DB). All values must match to 1e-6.

### 15.3 Integration tests (API, with a test PostgreSQL database)

- Login success/failure/lockout; role restrictions for each router (403 cases).
- Score endpoint: low, medium and high cases using a small test model (train a tiny XGBoost on a fixture dataset in the test setup) — check that alerts, holds, cases, notifications and audit entries are created correctly; idempotent repeat of the same `txn_ref`; `503` when no model is active.
- Full workflow: high-risk transaction → case `NEW` → assign → investigate → escalate → return → resolve (confirmed fraud: txn `DECLINED`, customer `high` risk) → close → reopen → resolve (false positive) → close.
- Alert dismissal releases a held transaction.
- Admin: create user, deactivate user (cases unassigned), update settings (bands change for the next scored transaction), activate model (hot swap, invalid model rejected).
- Reports return valid CSV and PDF.
- Audit log cannot be updated or deleted by the app DB user.

### 15.4 Performance test (`loadtest/locustfile.py`)

- Users post random demo transactions to `/transactions/score` with the API key.
- Scenario: 20 concurrent users for 5 minutes against the Docker stack.
- `make loadtest` saves `reports/loadtest_stats.csv` and a summary `reports/loadtest_summary.md` with average, median, 95th percentile latency and throughput. **Target: average < 500 ms** (Chapter Three NFR).

### 15.5 User acceptance test support

- `docs/UAT_QUESTIONNAIRE.md`: 12 statements rated on a 5-point Likert scale (1 = strongly disagree … 5 = strongly agree), grouped into usefulness, ease of use, clarity of explanations, and support for case handling; plus 3 open questions.
- `docs/UAT_SCRIPT.md`: 8 tasks for testers, e.g. "Find the highest-risk open alert and explain why it was flagged", "Dismiss a false positive", "Resolve an assigned case as confirmed fraud", "Escalate a case", (supervisor) "Assign an unassigned critical case", "Approve closure", "Download the fraud summary PDF".
- `scripts/uat_summary.py`: reads a CSV of responses and outputs mean and standard deviation per statement and per group to `reports/uat_summary.csv`.

### 15.6 Front-end tests

Vitest + React Testing Library for: login form, role-based menu, SHAP chart rendering, case action buttons shown according to `allowed_transitions`, currency/mask formatters.

## 17. Demonstration and simulator

### 17.1 `simulator/seed_history.py`

- Loads the **demo world** customers, accounts, security events and the **first 45 days** of transactions into the database with `status = HISTORICAL` (bulk insert; not scored; no predictions).
- Option `--anchor-now`: shift every timestamp so that day 46 starts at the current time (the history then ends "just now"). Store the offset in `data/synthetic/demo/anchor.json` for `stream.py`.

### 17.2 `simulator/stream.py`

- Sends the demo world's transactions from day 46 onward to `POST /transactions/score` in time order, and security events to `POST /security-events` just before their time.
- Options: `--rate N` (transactions per second, default 5), `--speedup X` (replay X times faster than real time; alternative to `--rate`), `--limit`, `--api-url`, `--api-key`.
- Prints a running summary: sent, approved, held, bands, errors, average latency; at the end compares predictions with the hidden `is_fraud` labels (confusion matrix) and writes `reports/demo_stream_results.csv`.

### 17.3 Makefile targets

```
make up           # docker compose up --build -d
make down
make data         # generate train + demo worlds, build features
make train        # train, evaluate, benchmark (if Kaggle files exist), register + activate best model
make seed-demo    # seed_history.py --anchor-now
make stream       # stream.py --rate 5
make demo         # up + data + train + seed-demo + stream (limit 2000)
make test         # backend + ml + frontend tests with coverage
make loadtest
make uat-summary
```

After `make demo`, open `http://localhost:5173`, log in as `analyst1@ifdims.local` / `Demo12345!` and the alert queue and cases fill up in real time.
